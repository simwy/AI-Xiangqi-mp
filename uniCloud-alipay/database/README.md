# 象棋数据库结构

当前为两张核心业务表：

| 集合 | 内容 |
| --- | --- |
| `xq_models` | 每个模型一条配置，包含接口、Key、think 开关和能力参数 |
| `xq_games` | 每局一条记录，普通对局、残局、导入及续弈共用结构 |

另有 xq_runtime（直播租约）、xq_votes（投票去重）、xq_requests（网关防重放）等辅助集合；不拆分每局步骤或解说。

本目录提供本地 schema 和索引定义，尚未部署到云端，也未执行远程建表或迁移。现有项目之前没有创建过象棋业务表，所以无需迁移已存在的步骤分表。

## 一局完整 JSON

`xq_games.steps[]` 按半回合保存棋谱，每项内嵌：

- 起终点、棋子、中文着法、落子前后 FEN 和提交时间。
- 本步总决策耗时、规则校验耗时。
- `calls[]`：每次模型请求及重试、实际 think 参数、耗时、Token 用量和脱敏错误。
- `commentaries[]`：完整报招、解说及各版本的 `audio[]` 文件信息。
- `events[]`：本步动画、字幕、语音的播放顺序和时间偏移。

开场、暂停和终局总结放根级 `calls[]`、`commentaries[]`、`events[]`。根级和步骤中的事件按唯一的 `seq` 合并即可还原整局时间线。正在执行但尚未合法落子的请求放 `pending_step`，落子提交时将其完整移入 `steps`；失败和重试不能丢失。

音频原文件保存在 uniCloud 云存储，JSON 仅记录 `file_id`、格式、时长、合成及上传耗时、SHA-256 和版本。不要存 Base64，不要把临时播放 URL 当作原文件地址。

结构化对象直接存入集合，**不要再 `JSON.stringify` 成字符串**；下载时才序列化成 JSON。

## 残局与导入

- `type`：`standard`（标准开局）、`endgame`（残局）、`continuation`（续弈）。
- `initial_position.fen` 和 `side_to_move` 保存初始棋盘及先走方。
- `source` 保存 FEN/JSON 导入来源，或来源棋局和续弈步号。
- 续弈创建新记录，不能覆盖来源棋局。
- `schema_version` 是文件格式版本；`version` 是当前记录的并发版本，两者用途不同。

参考文件：

- [标准开局](../../docs/examples/standard-game.json)
- [残局](../../docs/examples/endgame.json)
- [含落子、耗时和解说的完整示例](../../docs/examples/game-with-step.json)

示例不是自动初始化数据，不会开启付费调用。模型示例默认禁用且 Key 为空。导入服务仍需验证局面合法性、先走方、每步着法、事件 ID 和资源引用，不能仅凭 schema 通过就执行导入。

## 更新、回放与体积

服务端写入须匹配 `_id` 和旧 `version`，并原子递增版本；只有更新成功才广播落子。音频晚于落子生成时也要重新读取或定点更新对应步骤，不能用旧的整局快照覆盖最新棋谱。

列表只查名称、双方、结果等摘要；回放按需读取完整档案。达到实际服务空间的文档体积阈值前，使用 `archive.mode=file` 将完整 JSON 外置到云存储，棋局仍保持一条记录。外置时必须先成功上传，再通过版本校验切换 fileID；按 `archive.version` 和 SHA-256 读取，不能把空数组误当成没有棋步。体积阈值以部署空间实际限制和安全余量为准。

整局 ZIP 包含一份 `game.json`、音频文件及校验清单。导入时重新生成本库 ID、上传音频并替换 fileID，校验通过后再入库。

## 权限与部署

两个 schema 都禁止客户端直接读写；`xq_models.api_key` 另设字段权限。后台云函数维护配置，观众接口仅返回允许字段。棋局快照及导出文件不能包含 Key、Authorization 或完整私有推理。

在 HBuilderX 中关联正确服务空间，再上传本目录的 `.schema.json` 和 `.index.json`。这一步需要服务空间访问权限。持续对局、导入和回放已提供本地实现；上传定义仍不等于已完成云端部署或真实模型联调。
